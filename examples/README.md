# Сквозной учебный стенд лекций 1–13

MySQL 8.4, InnoDB, синтетические данные. Используйте отдельный локальный сервер или заранее проверенную новую учебную цель. `01_schema.sql` намеренно отказывается создавать уже существующую `service_training`: скрипт не удаляет существующую базу.

Порядок из корня репозитория:

1. `node scripts/check-input.mjs` читает CSV и сравнивает фактические заголовки. Пустой номер, неизвестный филиал и дубль заявки намеренно оставлены для обработки в staging.
2. Выполните `examples/sql/01_schema.sql`, затем `02_load.sql`, `03_verify.sql`, `04_objects.sql`, `05_roles.sql` через клиент MySQL с кодировкой utf8mb4. При работе с доверенным локальным сервером включите LOCAL и на сервере, и в клиенте (`mysql --local-infile=1 --default-character-set=utf8mb4 ...`). Пароль вводите интерактивно через `--password` либо используйте собственный login-path. Не записывайте действующий пароль в файлы проекта.
3. Внутри клиента из корня проекта можно использовать `SOURCE examples/sql/01_schema.sql;` и остальные файлы в указанном порядке. Команда `DELIMITER` в файле объектов относится к клиенту, передающему тело процедуры.
4. Для опыта индекса выполните `06_index_experiment.sql` один раз в чистом стенде. Повторное создание таблицы намеренно завершится отказом: прежний индекс нельзя оставлять в точке «до».

Исходный баланс: 6 строк requests.csv = 3 принятые + 3 отклонённые. Причины по порядку: UNKNOWN_BRANCH, EMPTY_REQUEST_NO, DUPLICATE_REQUEST_NO. В цели три заявки R101/NEW, R102/WORK, R103/CLOSED и четыре строки request_parts. Один перечисленный код детали означает quantity=1 по явному условию именно этого набора. Названия филиалов не уникальны, уникален code.

Для CALL найдите технический id по request_no. Успешное закрытие R101 сохраняет CLOSED, DIAG и одну строку журнала. Неизвестный код работы для открытой R102 должен откатить и UPDATE, и действие триггера. Процедура сама управляет транзакцией и вызывается вне уже открытой транзакции.

Владелец view заблокирован для входа и имеет чтение только отдельной учебной схемы. Viewer получает SELECT на v_open_requests. Для проверки создайте свою локальную учётную запись с паролем, назначьте ей роль командой GRANT и активируйте SET DEFAULT ROLE или SET ROLE. В новом подключении проверьте CURRENT_ROLE(), разрешённое чтение view и отказы прямого чтения/изменения requests. Это учебная граница прав; для рабочего проекта отдельно проверяют более узкую область необходимых объектов.

Автоматическая проверка на новом изолированном сервере: `node scripts/verify-sql.mjs --bin /path/to/mysql/bin --port 33317`. Скрипт не удаляет существующую схему, создаёт временную учебную учётную запись и сохраняет её параметры только в игнорируемой `outputs/sql/`. Отчёт с результатами не содержит пароль. После опыта остановите свой временный сервер. Программа не предназначена для запуска от администратора на рабочей базе.

Планы текущего опыта в `authoring/index-plan-example.json` получены на MySQL 8.4.13: ALL / rows=9799 → ref / rows=33. Фактических строк 10000, условию соответствуют 33. Оценки rows могут отличаться между запусками; время выполнения не измерялось. Генератор и оба EXPLAIN сохранены вместе с данными.

Полное описание входа и правил — `source-description.md`. В SQL классификация до CAST проверяет календарь и ограниченный список деталей стенда. Дополнительный сценарий `scripts/verify-course-sql.mjs` испытывает изменённые входные строки, контрольные запросы и роли. Его запускают после `verify-sql.mjs` на том же отдельном временном сервере; повторное создание тестового пользователя намеренно не маскируется.

Для опыта восстановления подготовьте второй пустой экземпляр той же версии MySQL с другим портом и выполните `node scripts/verify-sql.mjs --bin /path/to/mysql/bin --port SOURCE_PORT --restore-port RESTORE_PORT`. Копирование использует отдельную запись `training_backup`, параметры `--single-transaction --routines --events --triggers --no-tablespaces --set-gtid-purged=OFF` и локальный option-файл. Учебные серверы используют GTID OFF и не выполняют конкурентный DDL. Цель — новая схема с тем же именем на другом сервере. Пользователь DEFINER и роли поставляются отдельно, затем сверяются структура, все строки, поведение и неизменность источника. Файлы dump и option-файлы остаются в игнорируемом `outputs/`, отчёт без секретов — `reports/backup-verification.json`.
